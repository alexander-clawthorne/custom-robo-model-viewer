Custom Robo 3DS

Rebuild Custom Robo (GameCube, USA, GXCE01) to run on a Nintendo 3DS: arena battles and the story campaign. Everything is converted from your own disc on your own PC; no game data lives in the repo.

Also from the game's code: root motion (nodes 23-25, 0x80056104), mirroring (0x80053a20, touch screen to try it) and blending between motions (0x80052884; the viewer uses 10 frames).
Phase 3 · World data
12Donebg_data.BINArena collision decoded (tools/collision.py): 414 blocks and 3165 faces across the 40 arenas. Each block is a bounding sphere plus convex faces that carry their own plane; block 0 is the arena shell (four inward walls and a floor, no ceiling). Quads everywhere except arena 7, which uses triangles — nothing in the header says which, so the record stride is taken from the gap to the next block. The game’s own sweep (0x8005d08c) and face test (0x8005e270) confirmed the block flags and that the entry’s large trailing section is runtime scratch, not data. Cooked to romfs/collide and drawn on the 3DS as its own viewer category.
13In progress · aiming*_effect.BINWeapon and hit effects decoded (tools/effects.py). Each SFD entry of attack/gun/bomb/pod_effect.BIN is a container of its own holding two standard HSD archives; efc_common.dbn is that container without the SFD. 350 effect models are cooked and render on the 3DS. Their animation is stock HSD keyframes, and all 13,142 tracks now decode: joint transforms, material colour and alpha, texture UV and 4- or 8-frame flipbooks, plus a particle-trigger track whose keys carry only a frame. Correction: this step was planned around “HSD particles in leg_effect.BIN”; there are none. No joint in any effect file sets JOBJ_PTCL, and the particle track’s AObj has no flags and a null object id, so nothing in the files says what is spawned — only when. What each trigger fires must come from the DOL, keyed by the effect index. Still to do: play the animation on the 3DS, and find the spawn table in the code. Now fixing (2026-10-12): the gun muzzle flash plays on the 3DS but draws arena-sized. The animation cooker took the archive’s scene_data for the root joint, so every track landed on joint 0; the battle test also spawns a guessed effect index rather than the gun’s own. Since then (both fixed, checked on hardware): the gun’s effect is its own entry, gun id = effect entry; each bullet now carries the arrowhead model, turned along its flight, sized by the bullet and moving with it, with the animation at the game’s speed. Still open: the muzzle flash is coded but not visible on hardware; the fading trail (a ribbon in the game, not a model); the hit bursts on robots and walls; long shots still use the bead trail.
14Donesnr_map.BINStory maps decoded: all 94 entries parse. Each is a collision section in the same format as the arenas (one block per map, 7,671 faces in all), the map’s own HSD scene, the x and z extents, and an optional trailing container of further scenes. 1.17 M triangles of map geometry now render on the 3DS. rpg_f/t_models.BIN turned out to be mostly duplication: of its 579 sub-resources only 138 are field or town models, and the other 441 are byte-for-byte copies of snr_chara.BIN entries bundled per location — the resource id is the story-character index, so they were already on the 3DS.
15DonebmgText and font decoded (tools/bmg.py, tools/font.py). 26,694 messages across 102 BMG files, both languages, with the escape codes tallied — speaker and portrait, end of message, pause, ruby, colour, delay and sound cue. The font is four FONTbfn1 banks of 24×24 glyphs covering Shift-JIS. Checked end to end by drawing real messages with the game’s own font, in English and Japanese. Worth knowing: 915 of the 13,233 English messages are still Japanese, and snr_t_20.bmg is untranslated almost entirely (101 of 102) — that is on the disc, not a decoding fault.
16DonescenarioStory event scripts disassembled (tools/scr.py): 6,945 scripts and 91,170 instructions read with the game’s own names for all 7,092 scripts and all 300 opcodes, both recovered from tables the game ships. The interpreter is threaded — no dispatch loop — so each handler hardcodes its own instruction length; those lengths are what makes the stream decodable. Checked two ways that cannot both be luck: every script decodes exactly entry to entry, and all 12,468 CHAR_TALK instructions name a message that really exists in the paired BMG file — 100%, no misses. Scripts now read as scenes: camera, music, motions and dialogue in order.
17DonesoundSound decoded (tools/sound.py): 144 minutes of music across 73 .hps streams and all 392 samples in the 59 .ssm banks, 9 minutes of effects, every one decoding without error. It is all Nintendo DSP-ADPCM, and the 3DS takes that codec natively — libctru calls it NDSP_ENCODING_ADPCM, “DSPADPCM (GameCube format)”, and wants the same 16 coefficients the files carry — so converting is repackaging, not re-encoding and no quality is lost. The catch, read from the headers: ADPCM on the 3DS is mono only, so each stereo stream needs two DSP channels panned apart. The decoder checks itself: every stream block stores the history it should resume from, and across all 73 streams that matched 438 times with no mismatch.
18DonespriteMenu and HUD art decoded (tools/tpl.py): all 590 TPL files, 1,632 images, 40 million pixels, every one decoding without error. They are ordinary Nintendo TPL in formats gxtex.py already handled, so the only real question was that the image header gives height before width — the other order decodes without complaining, and was ruled out by checking each image against the gap to the next one. Button prompts, round numbers, HP bars and the 34 robot-body illustrations all come out clean.
Phase 4 · Robot assembly
19Donesrc/Robots assemble: a gun, a bomb launcher, two pods and four leg pieces hang off a body and move with it, so the viewer now composes nine models under one skeleton instead of showing one. Where each part goes came out of the game’s own draw code (0x80039fac): it writes the solved matrix of a rig slot straight into the part’s root and scales it by a tenth — weapon parts are modelled ten times robot size. The gun and the bomb launcher are forearms, mounted at the elbows, not held in the hands; the pods share the spine; the legs take a knee and a foot each. A part file holds more roots than the robot ever shows, and its two path lists tile exactly against the runtime arrays the loader fills, which is what settled the layout. Correction: this step was planned around “each part’s stored mount rotation”, and that rotation is a decoy. Every part root carries one — guns −90° about X, pods 90/0/90 — but the game sets JOBJ_USER_DEF_MTX | MTX_INDEPEND_PARENT | MTX_INDEPEND_SRT on that joint, so the stored value never reaches the screen; the geometry is already in the mount joint’s frame. Applying it rolled the guns onto their side and swung the pods off the back, which is how it was caught.
Phase 5 · Arena battles
20DonegameRobots run, jump and air dash in all 40 arenas against the arena’s own collision, and the app now opens on this battle test. The movement runs on the game’s own numbers. The part stats turned out to be compiled into main.dol, not shipped as files: five tables, one per part kind (tools/stats.py), with 34 bodies and 29 legs. The game combines body and leg into 15 movement stats: each body holds a minimum, normal and maximum for every stat, and the leg picks along it by percentage, 100 being normal. The leg labels confirm the reading — High Jump raises jump height, Wide Jump the air speed, the G+ and G− pair gravity, the verniers the dash length. From the movement code: run speed and acceleration, turn rate, a jump that rises only while the button is held, air steering with a speed cap, gravity, landing lag that grows with the fall, and the three kinds of mid-air dash, picked by a byte in each body: the straight air dash (Ray, Metal Grappler…), the air jump that is a second jump straight up (Little Raider, Aerial Beauty) and the long, steerable sky dash of the Lightning Sky models — each its own routine in the game’s action table. All 15 stats are now traced to the code that uses them. A self-checking test runs every movement on each robot and compares the result with the stats: 10 arenas and all three dash types pass, and the full jump lands on its designed height exactly. Correction: the first hardware build never left the floor — the jump was pressed, gravity ran in the same frame, and the robot landed again at once. The battle camera is the game’s too: a fixed view down the arena, pitched 30°, that pulls back and slides sideways every frame so both robots stay inside the frame with a margin — found in the camera-mode table as CAMMODE_MIDDLE. Landing a moving jump now skids, as the game does: the ground grips only when the change in velocity is small, and otherwise slides at a fixed rate. Correction (2026-10-12): not a fixed rate. Read instruction by instruction (0x8004c4a0–0x8004c73c, every vector helper disassembled), each sliding frame closes a fixed fraction of the gap to the target, vel += factor × (target − vel): 0.2 of it on an ordinary floor, snapping once within 2 hundredths. Nothing of the body enters it but the run speed, so heavier robots do not slide differently; faster ones carry more. The old rule had been inferred, not traced. Correction: 0x800333dc, first noted as the battle camera, is the results screen’s. Carried into step 21 and settled there: the wall sphere is the game’s own, sized and placed per body. Added (2026-10-12): the floor face’s kind word now drives the movement, as 0x8004b0a0 does. (kind >> 16) & 0xff picks one of six floor rows at 0x801c6c1c (threshold, slide fraction, grip; 0x8005d068); the only non-ordinary row the arenas use is 3, kind 0x30300 in arenas 12 and 16, an ice floor that closes 0.02 of the gap a frame. kind >> 3 == 1 is lava (arenas 2, 4, 8, 20, 23, 30, 38, 39): the robot hits itself for 100, is thrown straight up and lies down 50 frames as action 15. A low byte of 0x18–0x1c is a conveyor (0x8005cf0c). Spawn points over lava are moved onto solid floor; spawns are still a guess. The autotest drops the robot onto lava and judges the rise and the down time. Not ported: the game adds the conveyor’s velocity into the slide’s target and projects target and velocity onto the floor’s slope first; the port carries conveyors as a separate position offset.
21In progress · firing momentumgameRobots fight with every weapon on the game’s own numbers: gun, bomb, pod and tackle, hits, knockdown, rebirth and the end of a round. The three weapon tables are compiled into main.dol (64 guns, 52 bombs, 57 pods). A gun fires its volleys at a set interval, then recovers; each bullet passes through up to five phases with their own speed, homing rate, size and damage. Bombs do not fall under gravity: they fly a fixed arc to a cursor the stick moves while the button is held. Pods home along the floor on a spring that keeps them at hover height. Shots leave the real barrel: each part file lists effect-spawn joints, and the fire code reads one of them — now cooked for every gun and bomb. While firing, the gun arm reaches for the opponent and the bomb arm for the cursor, as the game’s aim stage does, so bullets fly along the forearm. Weapons also fire from inside a sky dash, which flies on. The tackle runs each body’s own three stages, homing in and armoured where the body says, and always knocks down. A hit is read by the victim on the next frame, as the game does: HP falls by the damage times the body’s defence, a down gauge fills, and past the body’s threshold the robot is knocked down instead of staggered, then rises with 30 frames of rebirth and 60 more of invulnerability. A KO ends the round with the winner’s pose; 2 minutes is the time limit. Checked by the battle autotest, which now fires every weapon, tackles, and times the knockdown, rebirth and invulnerability against the body’s numbers — 10 of 10 arenas pass, and the damage matches the formula exactly (a tackle of 126 on a 115% body: 161 HP). Corrections: the body value first read as HP is the knockdown threshold — every robot has 1000 HP; the gun fan turned the wrong way (Left Arc shot right); a tackle could never connect until it was exempted from the robots’ push, as the game exempts it. The button-0x80 move turned out to be the tag battle’s change of robot, not a 1-on-1 move. Correction: the CPU could stun-lock a robot, because every hit on a downed robot knocked it down afresh and restarted its down time. In the game such a hit throws the robot again and empties its gauge, but the down time runs on, so rebirth and invulnerability always come; juggled knockdowns now pass the same timing check. Each robot now carries the game’s own nameplate from us_battle.tpl: player tag, HP, the down gauge filling in its strip, and DOWN or REBIRTH above it (tools/hud.py, src/hud.c); where the game anchors it and how it colours the gauge are guesses. Left for later: the torso lean while aiming, the gun’s deploy animation, hitstop, effects instead of plain spheres (step 13), and the results screen (step 23). Now fixing (2026-10-12): shooting while running. The port stopped the robot dead for every weapon. In the game’s press code (0x80049924) the gun zeroes the velocity but keeps the run speed, the bomb zeroes both, and the pod touches neither. On the ground the gun handler (0x8004949c) keeps the run speed through the volleys and zeroes it only in the recovery after the last (once S+0x20c6 is the volley count + 1), and none of the three actions turns the robot’s facing. With the floor rule above, the robot is back up to speed along its old facing within a few frames while it fires, then slides to rest. Changed in the port: gun and pod as above, the gun’s movement along the facing it had at the press while the model is drawn turned to the aim; the floor rule corrected (step 20). A run-then-fire case in the battle autotest judges the gun’s first frame after the press, that the run speed holds through the volleys, and the frames to rest after the recovery, plus that the pods keep the run: 10 of 10 arenas pass at stride 4. How the joints and textures came out right

Nothing was guessed into place: each fix was checked against code that already runs these formats correctly.

Joints

Custom Robo is built on HAL's sysdolphin engine, the same one as Melee. The Melee decompilation has turned that engine back into readable C, so the joint layout (position, rotation, scale, children) and the order rotations apply in come straight from it.

The one hard bug was the arms and legs. They are inverse-kinematics chains, and reading the engine's own code (resolveIKJoint1, resolveIKJoint2 and the effector case in jobj.c) showed the rule: a chain is only solved when its end joint has a target, and otherwise the end joint is placed one bone length along its parent. Using that rule put every limb where it belongs.

Animation used the same approach one level up: the motion code in the game itself was decompiled with Ghidra (REA cannot open PowerPC), and its two-pass solve was rebuilt step by step.

melee: jobj.c · doldecomp/melee · HSDLib (HSD file layouts)

Textures

GameCube textures are compressed and stored in small tiles. The decoder follows the formats as Dolphin (the GameCube emulator) implements them, and each result was checked with a PC render before going near the 3DS.

The 3DS stores textures in its own tiled order. The first 3DS build had scrambled colours because the image was flipped twice. The fix was to encode a test image with devkitPro's own converter, tex3ds, and change the cooker until its output matched byte for byte.

Dolphin: TextureDecoder_Common.cpp · devkitPro/tex3ds · devkitPro/citro3d

How it was checked

Two independent checks every time. A software renderer on the PC draws each model straight from the decoded data, so decoding mistakes show up without the 3DS involved. Then an automated Citra run steps through every category and screenshots it, which catches anything that only goes wrong on the 3DS GPU.

Code: tools/hsd.py · tools/gxtex.py · tools/cook.py (private repo)

Watch-outs

Gameplay has no head start

The MKW port borrowed Kinoko's finished physics. Nothing like that exists for Custom Robo, so movement, weapons, damage and AI are rebuilt from the game's PowerPC code and observation. This is the largest phase by far.

Bombs might be sideways

Resolved, and the premise was wrong: the rotation stored on a part is never used by the game, so there is nothing to keep. Browsed alone every part now stands in its own frame; assembled, each one takes its mount joint’s orientation from the body. Confirmed on hardware.

Feet in the bind pose

Resolved: feet point forward once a motion plays. They only lie sideways in the bind pose, which X / SELECT can still step to.

Some arenas are only sky

Arena entries 1, 8, 15, 38 and 39 are space backdrops without a floor; one entry is a ? model.

Size on the SD card

The viewer is now 405 MB because vertices are stored unindexed; the story maps alone added about 150 MB. Indexing (step 27) should cut that a lot, and may need doing sooner than planned.

Citra input

Your Citra profile is controller-only, so emulator checks use the AUTOTEST build and background screenshots instead of key presses.
